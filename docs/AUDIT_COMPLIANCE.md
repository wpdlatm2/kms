# 감사 기능과 증적 — 금융감독규정 · ISMS-P 대응

pqc-kms 관리시스템이 남기는 감사 기록과 증적의 구성, 규정 항목과의 대응, 운영자가 직접 정해야 하는 사항을 정리한다.
이 문서는 **제품 기능의 자기평가**이며 인증·심사 결과가 아니다. 법정 보관기간과 검토 주기는 기관의 정책에 따라
운영자(준법·정보보호 담당)가 확정해야 한다.

## 1. 무엇이 기록되는가

세 개의 로그는 서로 섞이지 않는다 (`client` / `admin` / `console`). 모든 항목에는 다음 필드가 있다.

| 필드 | 의미 |
|---|---|
| `seq` | 로그별 연속 순번 (누락·삽입 탐지) |
| `time` | UTC, 마이크로초 |
| `who` / `via` | 행위자(사용자 또는 인증서 CN) / 사용자를 대신 주장한 중계(콘솔) |
| `plane`, `kind` | 클라이언트·관리·콘솔 / 요청(프로토콜) · 이벤트(서비스가 한 일) |
| `category` | `authentication` 인증, `key-lifecycle` 키 수명주기, `key-access` 키 조회·반출, `permission-change` 권한 변경, `audit-access` 감사로그 접근, `api-access`, `system`, `audit-maintenance` |
| `outcome` / `result` | `success` · `failure` · `denied` / 상세 결과 |
| `op`, `target`, `detail` | 동작, 대상(키·그룹·클라이언트), 변경 전후 내용 |
| `approval`, `owner` | **승인번호**, **담당자** (권한 부여·변경·회수) |
| `remote`, `requestId` | 접속 IP, 응답으로 돌려준 `X-Request-Id` (요청-응답 대조) |
| `prev`, `hash`, `mac` | 해시 체인, HMAC (아래 2절) |

기록되는 사건: **로그인 성공·실패(사유 구분)·계정 잠금·잠금 해제·비밀번호 변경/실패·계정 생성/재설정·보안 설정 변경·서비스 시작/중지/재기동**, OTP 사용·복구코드 사용, **TLS 핸드셰이크(인증서) 실패**, 키 생성·활성·비활성·침해·회전·파기·이름 변경,
**키 값 반출(get)과 거부**, 권한그룹·상위그룹·권한 템플릿·클라이언트 매핑·관리자 위임의 모든 변경(변경 전 내용 포함),
권한 없는 시도, **감사로그 자체의 조회·검증·내보내기·검토**, 기동·종료, 보관기간 경과 파일 삭제.

### 승인번호·담당자 (권한 부여 증적)
모든 클라이언트 매핑, 관리자 위임, 권한 템플릿 변경은 **승인번호(`^[A-Za-z0-9][A-Za-z0-9._/#-]{0,63}$`)** 없이는 거부된다.
매핑·위임은 **담당자**도 필수이며, 서비스그룹·상위그룹도 담당자를 가진다. 거부된 시도도 로그에 남는다.
화면과 API에 승인번호·담당자·부여자·부여시각이 표시되고, 증적이 없는 기존 부여는 `missingEvidence`로 표시된다.

## 2. 위·변조 방지

* 각 항목의 `hash`는 항목 내용과 직전 항목의 `hash`를 SHA-256으로 묶은 **해시 체인**이다.
  항목을 삭제·수정·삽입·순서 변경하면 그 지점부터 체인이 끊어진다.
* `mac`은 `hash`의 HMAC-SHA256이다. 키는 로그 파일 옆에 두지 않고 `-master-hsm` 사용 시 **TPM에 묶여 봉인**된다.
  키가 없는 공격자는 파일을 고친 뒤 체인을 다시 계산해도 유효한 MAC을 만들 수 없다 (테스트: `TestRecomputedChainNeedsTheKey`).
* **검증**: 콘솔 감사·로그 탭의 「무결성 검증」 또는 `GET /admin/v1/audit/verify?log=admin|client` (콘솔 로그는 `log=console`).
  순번 단절, 체인 불일치, 내용 변조, MAC 불일치, 말미 절단을 구분해 위치와 함께 보고한다.
* 일 단위로 파일이 분리되고(`*-YYYYMMDD.jsonl`) 체인은 파일을 넘어 이어진다. 비정상 종료로 잘린 마지막 줄은 기동 시 복구되고 그 사실이 기록된다.
* 변경 이벤트와 모든 실패·거부 항목은 기록 즉시 `fsync`로 디스크에 반영된다.
* 로그를 쓰지 못하면 표준 오류로 알리고 메모리·체인 상태는 유지한다 (서비스 거부 방지와의 절충).

## 3. 보관과 반출

* `-audit-retention-days` (기본 1825일 = 5년): 이보다 **젊은 파일의 삭제는 거부**된다. 애플리케이션은 스스로 삭제하지 않으며,
  삭제 시 어떤 파일을 지웠는지 체인에 먼저 기록된다. 기본값은 예시이므로 기관 정책(예: 금융회사 전자금융거래 기록 보존 기준)에 맞게 설정한다.
* **증적 내보내기**: 조건(기간·분류·결과·사용자·검색어)에 맞는 항목을 ZIP(`<log>-audit.jsonl` + `manifest.json`)으로 받는다.
  매니페스트에는 내보낸 사람·시각·조건·체인 검증 결과·체인 머리값·데이터 SHA-256이 들어 있고, 수신자는 항목의 체인을 다시 검증할 수 있다.
  내보내기 자체도 로그에 기록된다.
* **외부 보관**: `-audit-syslog=tls://collector:6514` (또는 `tcp://`)로 RFC 5424 형식(facility 13, 심각도는 결과에 따름) 전송.
  수집기 장애 시 큐가 가득 차면 오래된 항목을 버리고 복구 시 누락 건수를 알리는 항목을 보낸다. 로컬 체인 로그가 기준 기록이다.
  백업·원격 보관은 운영자가 수행한다.

## 4. 열람 통제 · 정기 검토

* 감사 데이터(조회·검증·내보내기·검토)는 **전체 범위(ALL) 관리자 또는 감사 권한자**만 사용할 수 있다. 서비스 범위 위임자는 거부된다(거부도 기록).
* 감사 권한은 읽기 전용이다. 키 값은 관리 API 어디에서도 나오지 않는다.
* **정기 검토 기록**: 검토자가 로그와 기간, 결과(`이상 없음`/`이상 발견`+내용), 결재번호를 남기면 검토 이력으로 조회된다.
  검토 주기(월·주 등)와 이상 징후 처리 절차는 기관 정책으로 정한다.

## 6. 한계와 운영 책임

* 체인은 **변조를 탐지**하며 방지하지는 않는다. 호스트 루트 권한을 가진 사람은 파일을 지울 수 있고, 말미 절단은 이전에 내보낸·전송한
  체인 머리값과 비교해야 확실히 드러난다 → 외부 syslog 전송과 주기적 내보내기를 권장한다.
* 콘솔 로그의 MAC 키는 파일(`<log>.key`, 0600)로 보관한다. 백엔드 로그의 키만 TPM에 봉인된다.
* 개인정보 포함 여부: 기록에는 사용자 ID·IP·키 이름이 들어간다. 키 값·비밀번호·OTP 코드는 기록하지 않는다.
